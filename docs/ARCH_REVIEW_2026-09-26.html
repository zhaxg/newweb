两个 P0：都已复现，且第一个已进入生产产物

这两条不是「优化建议」。第一条会让按既定意图部署的站点直接报错，第二条让每个用户多下 115 KB 永远不执行的代码。两者我都逐字节复核过，不是推断。

P0 · 正确性

gzip 预压缩产物是陈旧快照，entry chunk 已损坏

vite.config.ts 的 hmxGzipAssets 在 generateBundle 钩子里压缩， 而这个钩子跑在 Vite 自己的 vite:build-import-analysis 之前——后者才负责把 __VITE_PRELOAD__ 替换成 __vite__mapDeps([...])。 于是 .gz 里装的是替换之前的快照。

entry chunk index-Bkt8svBV.js字节__VITE_PRELOAD__mapDeps 定义
源文件（正确）1,682,44401
.gz 解出的内容1,340,7946,5270

调用形态是 ()=>import(`./IconAbacus-*.js`), __VITE_PRELOAD__——第二个实参在调用时求值， 是个没有任何声明的自由标识符。任何懒加载图标触发时抛 ReferenceError: __VITE_PRELOAD__ is not defined。

触发条件
服务器配了 nginx gzip_static / IIS 静态压缩。而这正是 vite.config.ts:9-10 注释写明的目标用法——即按设计意图部署就会踩到。未配预压缩则退化读原文件，无影响。
规模
184 个 .gz 中 7 个陈旧（clean rebuild 后稳定复现），含 entry chunk 本身。
修法
钩子从 generateBundle 改为 writeBundle，从磁盘读已落盘的最终文件再压。已实测：184/184 逐字节一致，构建耗时无变化。
代价
修好后首屏传输上升 76 KB（509 → 585 KB gz），因为正确副本更大。这是修复的必要代价，不是回归。
P0 · 体积 + 信息暴露

mock 数据整包进了生产产物

src/api/_core/request.ts:9 静态 import { mockAdapter }，第 25 行 if (USE_MOCK) instance.defaults.adapter = mockAdapter。 生产构建把 USE_MOCK 内联为 false，所以mock 不会真的生效—— 但模块和全部种子数据照样进了包。

口径要说准：这不是「生产在跑 mock」。flag 是好的、红线没被破。问题是 死重（每个用户下载 115 KB gz 永不执行的代码）+ 内网标识暴露 （线上 JS 里可搜到 gluenet.kvfileds、hmx.Service.Widgets.Services 等）。
生产 request-*.js 中的 mock 指纹命中
gluenet.kvfileds1
GanttCCMProcEditJCInfo1
hmx.Service.Widgets.Services1
mock-token1

chunk 实测 1,419,801 B，其中 27 个 >5KB 的字符串字面量合计 910 KB（占 68%）， 最大一条 575 KB 来自 gantt_data.json。剥离后约 421 KB 原始 / 83.5 KB gz。

修法
改为条件动态 import()（if (USE_MOCK) instance.defaults.adapter = (await import("@/mock/mockAdapter")).mockAdapter），或构建期把 mock 目录 alias 到空实现。
收益
首屏 509 → 约 394 KB gz（-23%），同时消除线上 JS 里的内网标识。
注意
要同步处理 5 个幽灵依赖（见「顺带发现」），且 dev 下 mock 必须照常可用。
文档也要跟着改：README 与 AGENTS 都写着「生产构建不会带 Mock 适配器与演示数据」。 按上面的实测，这句不成立——flag 正确，但数据在包里。这句话本身有误导性，建议改成 「flag 已钉死 false，mock 不在生产生效；但模块与种子数据仍会打进产物，待按 P0-2 收敛」。

路由设计对标

两个项目在路由上走的是同一条路：后端菜单 → 路由记录 → 菜单投影，单真源、不做第二份数据。 差别在契约的显式程度。总体判断：newweb 的运行时设计更稳， tdesign 的类型与约定更显式——值得互相借的正好是对方强的那一半。

值得从 tdesign 借的三点

  • 组件解析的防御性写法。utils/route/index.ts:58-80 不是简单查表： glob key 规范化后全等匹配，命中多个直接 throw 并在报错文案里点明「同目录同名 .vue/.tsx」， 未命中则 warn + 退回错误页而不是白屏。自研平台最容易在「菜单配错一个字符」上翻车，这个结构值得照抄。
  • 无路径父路由包深层菜单。utils/route/index.ts:83-109：当 component 不是布局时，把自己塞进 children、自身换成布局、path 置空。 这样后端返回一棵不整齐的树也能渲染 /a/b/c，比要求后端吐规整两层树务实得多。
  • 升级到 vue-router 5。v5 已把 unplugin-vue-router 并入核心 （vue-router/vite + 生成的 typed-router.d.ts），类型安全路由与文件式路由 是稳定特性，官方定位为对 v4 无破坏性变更的过渡版本。对标项目已经用上了，newweb 还差一个大版本。 注意 Data Loaders 仍是实验特性，别碰。

newweb 反过来更稳的两点

  • 缓存键不依赖人工契约。tdesign 把「缓存键 = 路由 name」这个隐式约定完全交给开发者维护， 而它自己已经出现了 TopPanel.vue 与页面同名 DashboardBase 的踩线写法。 newweb 的 pageId#世代号 由框架算，规模上去不会错。
  • 退出即整体移除。newweb 的三阶段把「登出清理」做成一个原子动作； tdesign 靠 afterEach 里判断 path === '/login' 再逐条 removeRoute， 逻辑散在守卫尾部，漏一个条件就残留。

两边都缺的

没有一处同步 document.title。两个项目的浏览器标签页标题永远停在 index.html 的静态值，多页签场景下用户完全无法从标签页区分页面。这是低成本高体感的缺口， 在 afterEach 里加一行即可（newweb 的 guard.ts:61 已经有现成的 afterEach）。

两个被澄清的常见误判

  • 不是「日期库重复」。dayjs/moment/date-fns/luxon 全都没装。产物里 74 个 locale-*.js（8.55 MB）全部来自 Univer 的 CLDR i18n。
  • 图标体积不在 entry 的 SVG 体里，而在它的索引表里。6184 个图标体各自只有 0.43 KB、 确实独立成 chunk（懒加载机制本身是对的）。entry 里那 917 KB 是 6202 条 key → 懒加载器的映射表。所以收益来自「砍注册表」，不是「改按需加载」。

顺带发现

仓库卫生（总体良好）

  • 479 个追踪文件，最大 900 KB（gantt_data.json 演示数据），无误入库的二进制；dist/temp/.code-graph 等均已在 .gitignore。
  • 残留 worktree 可清理：worktree-rustling-cooking-newt 分支的内容 已完全包含在 main 内（落后 13 个提交），.claude/worktrees/ 下那个目录是空壳。

依赖健康度

  • 5 个幽灵依赖：@univerjs/core、/drawing、/docs-drawing、 /sheets-drawing、/drawing-ui 被直接 import 但未在 package.json 声明， 只作为 @univerjs/presets 的传递依赖存在。上游一升版调整子依赖，构建立即断裂。
  • React 混入 165 条传递依赖：@univerjs/* 拖进 react + react-dom 及 @radix-ui/*（2.5 MB）、sonner、cmdk，且实测真的进了产物 chunk。
  • 图标库实际 5 套并存：@tabler/icons-vue（72 MB，66 个在用）、 @tabler/icons（50 MB，0 处直接引用）、@primeicons（0 处引用）、 以及 PrimeVue / Univer 各自内部的一套。前两个可清。
  • vite.config.ts:56 的 tabler-icons alias 指向正确但是死代码—— 全仓 from "tabler-icons" 引用数为 0，301 处全走 barrel，从不经过它。 它想解决的正是按需引入问题，但没人用。
